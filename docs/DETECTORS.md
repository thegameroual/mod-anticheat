# Movement signals and their limits

The engine adapter takes a value snapshot before the core relocates the mover. Only server state authorizes exemptions, flight, movement speed, water walking and forced movement. Incoming transport, flight, falling and swimming flags cannot grant a general exemption. Detectors return evidence; they cannot kick, ban, access SQL or retain engine pointers.

`MovementTests.cpp` exercises the algorithms independently of AzerothCore. These tests validate arithmetic and state transitions, not the completeness of the adapter or actual game physics. Gameplay verification is required, especially for doors, scripted movement, aura removal and spells supplied by other modules.

| Signal | Suspicious behavior and data | Exemptions and limits | Automated coverage |
|---|---|---|---|
| Speed | Accumulated travelled distance exceeds an integrated **server receipt time** budget over a configurable window. Ground movement uses XY; server-authorized swimming and flight use 3D. Oversized same-time bursts are checked immediately against a full window's allowance. | Server teleports, forced movement, vehicles and explicit bounded transitions reset the baseline. Validated transports use local coordinates and remain speed-checked. Speed changes use the greater of adjacent server speeds. Latency adds one capped allowance per window, never per packet. Legitimate packet batching can still resemble excessive travel; no physical speed estimate from receipt time is perfect. | Normal running, excess speed, old >3x bypass, zero-interval packets, forged transport/fall/flight flags, high/variable latency, server speed changes, local transport motion. |
| Fly | Incoming flying/can-fly flags lack server flight authority. | Flight authorization and an expiring aura-removal grace. A client that moves vertically without those flags can evade this signal; geometry and physics signals provide review evidence only. | Authorized flight, removal transition, exact expiry, bounded movement-order grace. |
| Teleport | Position discontinuity from the preceding server position exceeds the greater of the configured threshold and time-dependent travel allowance. | Server teleport/forced motion and map changes reset tracking. There is no minimum packet interval. Falling vertical distance is not a teleport proof; XY remains checked. Long observation gaps produce only diagnostic evidence when travel is still excessive. Server scripted relocations without observable orders need gameplay review. | Authorized Blink/teleport, Charge/knockback, same-timestamp illegal teleport, map change, vehicle/transport exit, gap diagnostic. |
| Climb | Large steep ascent, including purely vertical ascent. | Skips server flight/swim/slow-fall and jump/fall contexts. **Diagnostic only**: slopes, stairs, elevators and collision height cannot be reconstructed from two positions. | Shared movement scenarios; geometry validation in game remains necessary. |
| Jump | Repeated jump opcode while a previous jump remains active and a valid sampled terrain height is more than three yards below the player. | Flight, swimming, slow fall, landing and grounded samples reset state. Lost landing state expires after ten seconds. Invalid height creates no evidence. **Diagnostic only**: height does not prove a player was not on an object. State transitions run even when gravity detection is disabled. | Normal and double jumps, missing landing, invalid terrain, gravity detector disabled. |
| Gravity | Sustained airborne falling with much less drop than a conservative gravity envelope. | Server flight/swim/slow-fall reset state; rising movement updates the observed apex. Terrain must be valid and more than three yards below the sample. **Diagnostic only**: network receipt time is not a physics clock; auras, moving objects and scripted motion require review. | Normal fall, reduced-drop trace, slow fall, invalid height. |
| Waterwalk | Water-walking flag without server authority. | Server water-walk/ghost authority and an expiring removal transition. Does not report “swimming on land” from a pre-relocation water lookup. Does not detect clients walking on water without setting the flag. | Authorized swimming/water walking, removed authority, swimming transition. |
| NoFall | Gravity-disabled flag without flight or fall-modifying authority. | Fall/flight permissions and expiring removal transition. **Diagnostic only** and named “Gravity flag” in reports: this does not establish suppression of fall damage. The module does not claim to measure missing fall damage. | Unauthorized flag, safe fall and grace expiry. |
| IgnoreControl | Horizontal displacement from a stable anchor while the server reports rooted/stunned state. | Bounded control/latency transition; forced movement and authoritative transport handling. Uses total displacement, so sub-yard packets do not bypass it. Residual movement during initial acknowledgement grace is intentionally tolerated. Server scripts that relocate rooted players must be validated. | Root/stun shared authority, stationary target, sub-yard movement, control removal. |
| FakePing | Client-clock progression differs from server progression over a window. | Unsigned subtraction supports the normal 32-bit client timestamp rollover. Client timestamps never increase the speed allowance. **Diagnostic only**: clock jumps, queue bursts and latency are not proof of deliberate cheating. | Rollover, backwards timestamps, network bursts, latency variation. |
| NoClip | Rate-limited blocked line of sight along a movement segment, or an inconsistent transport-frame claim. | Ground-oriented segments only for line of sight; excludes server transport/vehicle/forced motion and flight/swim/jump/fall contexts. **Diagnostic only**: line of sight and player collision differ; doors, dynamic models, phases and geometry defects can all cause false positives. No single result can authorize a sanction. | Query rate limit, blocked-line diagnostic, invalid ground query rate limit, malformed transport claim; doors/phases require in-game testing. |

Gravity constants match `Movement/Spline/MovementUtil.cpp` in AzerothCore commit `a4b1f8a040fa82782b34578bc37293f215d0e908`: approximately 19.291105 yards/s² and terminal speed 60.148003 yards/s. The implementation uses a deliberately broad 25% envelope and does not claim a complete reproduction of the client's physics.

All movement state is session-local. Reconnection creates a fresh state. Map changes, server motion, exemption exit and long sample gaps rebase accumulated distance and airborne state. The adapter must never derive an indefinite grace from a client ACK. Malformed non-finite positions cannot enter the tracking baseline. Sample gaps reduce confidence; interrupting the observation stream remains a limitation of a passive detector.

Permission orders use separate deadlines: toggling water walking or feather fall cannot waive speed, flight or teleport checks. An actual server speed change temporarily permits the greater of the relevant old and new server speeds while retaining accumulated distance and elapsed time. Excessive travel is checked throughout that interval. Repeated identical correction orders cannot renew it. Full movement grace is reserved for lifecycle and authoritative displacement transitions.

Transport membership in this core can originate from a client flag, so a non-null `GetTransport()` alone is insufficient. The adapter validates finite bounded offsets and consistency with the vessel's server transform before using local coordinates. Frame changes establish a reference at the server position without clearing accumulated evidence. A local/world discrepancy on a claimed transport cannot trigger the automatic rebase used for a completed server spline on land: the core consumes those client positions at different points. These checks do not prove collision with the deck; unusual transport models and dynamic elevators still need gameplay validation.

Changing a validated transport coordinate frame preserves the speed and clock observation windows. Rooted displacement already established in the previous frame is retained as a scalar and added to displacement from the new anchor. This avoids granting fresh movement tolerance by repeatedly changing frames. It can conservatively overestimate net movement when several frame changes contain small opposing position adjustments; rooted players on rotating vessels require gameplay validation.

Ground and line-of-sight requests have separate timers sharing the configured minimum interval. An attempted invalid ground lookup consumes the interval too. No detector allocates a string or writes to a database on the packet path. A fixed-size result batch carries static reasons and measured values to scoring and persistence.

Before enforcement is enabled, capture and review normal and suspicious traces on the intended server: all mount types; flight removal; Blink, Charge and knockback; transport boarding and disembarking; vehicles and possession; jumping from dynamic objects; feather fall and safe fall; roots during falling/knockback; inter-map and same-map teleports; high latency and queued movement bursts. Tune the configuration from those traces and retain observation mode until false positives are understood.
